# 管理后台 UI 工程与样式规范

本文是 `sitkin-pb-backend-management` 管理端的长期 UI 规范，适用于新页面、重构和被改动的既有页面。它不是一次性改版记录，也不表示所有历史页面已经满足每一项；修改某个业务面时，应让该业务面达到本文标准，并明确留下的技术债。

## 1. 产品定位与设计方向

这是现场运营和内容配置工作台，不是营销页。设计目标按优先级排序为：

1. 操作含义明确，降低误发、误删、误核销和错误上线的概率。
2. 信息密度适中偏高，长列表和复杂配置仍可扫描。
3. 同一业务在桌面、平板和手机上都能完成，不依赖“回电脑再操作”。
4. 视觉克制、可信、稳定；动效只服务反馈、状态变化和定位。

维持现有 React 19、Refine、Ant Design 5 和蓝灰色运营工作台。视觉变化幅度保持低，运动强度保持低，数据密度保持中高。不要引入第二套 UI 框架，也不要使用营销页式渐变、玻璃效果、发光、持续装饰动画、表情符号图标或手绘 SVG 图标。

## 2. 设计系统和实现入口

以下文件是现有设计系统的主要入口：

| 位置 | 责任 |
| --- | --- |
| `src/contexts/color-mode/index.tsx` | Ant Design 深浅色算法和全局 token |
| `src/styles/admin.css` | 工作台布局、语义类、响应式和减少动画规则 |
| `src/game/ui.tsx` | `PageCard`、`Field`、`AdminTable`、`EditorDrawer` |
| `src/game/guidance.ts` | 页面和字段运营说明 |
| `src/game/components/` | 可跨业务面复用的领域字段、预览和展示组件 |

实现新界面前先搜索已有模式。优先扩展共享组件或领域组件，不在页面内重新实现抽屉宽度、表格滚动、字段帮助、时间格式和空状态。

- 颜色、圆角、控件高度、文字和边框优先来自 Ant Design token 或现有 `--admin-*` 变量。
- 同一语义只使用一种颜色。成功、警告、错误、信息和只读状态使用组件 token，不靠任意十六进制色值。
- 深色模式必须与浅色模式一起设计。修改主题 token 时同步检查 CSS 变量，避免两套值漂移；后续若继续扩展主题，优先抽取单一 token 源。
- 统一使用 `@ant-design/icons`。只有确实没有对应图标且通过设计评审时才增加新图标来源。
- 阴影和圆角只表达层级，不作为装饰。避免卡片套卡片；同一表面内优先用标题、间距、分隔线和折叠分组建立层级。

## 3. 页面、列表和信息层级

- 标准业务页使用 `PageCard`：页头包含唯一 H1、简短业务说明和当前页主操作，主体承载筛选、指引和内容。
- 一页只突出一个主操作。危险操作与日常操作分组，不能紧贴默认主按钮，也不能只靠红色区分。
- 工具栏允许换行；搜索和筛选在手机上占满可用宽度。不要为“对齐”设置会导致窄屏溢出的固定宽度。
- 业务表格使用 `AdminTable`。列设置可读最小宽度，页面本身不横向滚动；列多时只允许 `.admin-table-region` 内横向滚动，并显示提示。
- 操作、状态和短标签不能压成一字一行。长中文标题、URL、ID 和原因要么安全换行，要么有可访问的截断与查看方式。
- 空状态说明“为什么为空”和“下一步能做什么”；没有权限、筛选无结果和业务尚未创建不能共用含糊文案。

## 4. 表单和高密度配置

表单默认使用垂直标签。占位符只能举例或提示格式，不能代替可见标签。帮助文字说明影响范围和不可逆后果，错误信息紧邻字段。

### 4.1 Ant Design 绑定约束

`Field` 中的实际输入控件保持为 `Form.Item` 的唯一直接子节点，让 Ant Design 接管 `value` 和 `onChange`。不要为了加说明再包一层 `div`，否则可能破坏初始值、校验、数组字段和保存。

跨 Tab 保存时，只有确实需要参与整表序列化和校验的内容才使用 `forceRender`。既然隐藏 Tab 参与校验，`onFinishFailed` 就必须自动切换到首个错误 Tab、展开对应折叠项并滚动到字段，不能只显示“保存失败”。

### 4.2 字段布局

- 双列只放互相独立的短字段。正文、URL、媒体选择、帮助文字、复杂校验和预览占整行或单独分区。
- 条件字段只在当前模式有效时显示；例如 `custom` 媒体模式必须要求对应 URL，非 `custom` 时明确说明已有 URL 是否被忽略。
- 类型能力使用单一映射维护，包括可选类型、主内容要求、是否支持自动展示和是否支持完整预览，避免多个页面各写一组字符串白名单。
- 修改线上内容、现场干预和高风险配置必须展示原因字段、影响范围、乐观版本或并发状态。冲突不能被普通网络错误吞掉。

### 4.3 重复子资源

预计超过 5 条的线索、关卡或规则使用“摘要列表 + 单项渐进展开”，不要一次展开十几张完整表单。每个摘要至少包含稳定序号、类型或状态、内容摘要和可用操作。

- 新增或复制后展开新项并聚焦主要字段。
- 排序必须有键盘可用的上移、下移按钮，不能只提供拖拽；操作后保持焦点并向辅助技术宣布新位置。
- 删除前说明是立即删除、保存后归档还是仅从草稿移除。可恢复时优先提供撤销。
- 保存失败后保留草稿、顺序和展开位置。关闭 dirty 抽屉前明确确认，不能静默丢失十几条配置。
- 预览必须验证真实业务语义，例如“刚答完”和“历史已答”，不能只做静态漂亮样张。

## 5. 抽屉、弹窗和操作反馈

- 多分区长表单、预览和高密度编辑使用 `EditorDrawer`；短原因表单、确认和不可逆提示使用 Modal。不要在 Modal 内承载完整业务编辑器。
- Drawer wrapper 保持 `max-width: 100vw`，底部固定承载关闭和主操作，并包含 `env(safe-area-inset-bottom)`。主操作始终可见，不要求用户滚回顶部。
- 保存中阻止重复提交。若请求已经提交，关闭按钮、遮罩和 Esc 的行为必须可预测，避免界面关闭后用户误以为没有保存。
- 最多同时保留两层长期业务编辑容器；删除或 dirty 等短暂确认 Modal 不计入，但只能覆盖最上层，关闭后必须把焦点还给发起控件。关闭主编辑器后，焦点返回列表中的原操作按钮。
- 查询错误、保存失败和版本冲突在编辑器内使用持久 Alert，不只依赖短暂 Message。版本冲突至少提供“刷新最新数据”和“保留或复制当前草稿”的清晰路径。
- Loading、保存结果、排序和冲突信息使用 `role="status"` 或合适的 `aria-live`，但不要重复朗读整页内容。

## 6. 响应式规则

响应式以组件实际可用宽度为准，尤其是 Drawer 和分屏窗口；不能只看浏览器 viewport。复杂编辑器优先使用 container query，暂时无法使用时按以下区间提供明确回退：

| 可用宽度 | 布局要求 |
| --- | --- |
| `≥ 1200px` | 完整桌面工作台；双列表单，线索表单与预览可双栏 |
| `992-1199px` | 紧凑桌面；保留主要桌面布局，显示表格横向滚动提示 |
| `768-991px` | 平板或分屏；移动导航，复杂抽屉优先单列，短字段可双列 |
| `576-767px` | 窄平板或大屏手机；复杂编辑器必须单列，工具栏和摘要操作换行 |
| `≤ 575px` | 手机；单列表单、16px 文本输入、弹层夹紧视口、日期时间面板纵向化，预览取消 sticky |

共同约束：

- 页面根布局宽度不得超过 viewport；表格可以在自身容器横向滚动。
- 抽屉、Modal、Picker 和上传选择器不能超出视口；软键盘弹出后仍能访问当前输入和主操作。
- 手机主要按钮和重复编辑操作的触控区域尽量不小于 44px；桌面密集操作可沿用 36px 控件高度，但必须有清晰间距和焦点样式。
- 手机不靠减小字号塞下桌面布局。标题、说明、操作区和双栏都要有显式重排。
- 只要两栏任一栏低于约 300px，就应转为单列，不继续挤压预览或表单。

## 7. 状态和无障碍基线

每个异步编辑面都要评估以下状态，并覆盖该业务实际可能发生的项目：

| 状态 | 必须表现 |
| --- | --- |
| 首次加载 | 骨架或带可读文字的 loading |
| 局部刷新 | 保留旧内容并标明刷新中；数据失效时禁止保存 |
| 空数据 | 原因和下一步动作 |
| 校验失败 | 打开错误 Tab 或折叠项，聚焦首错 |
| 保存中 | 主按钮 loading，防重复提交和提前关闭 |
| 成功 | 重新读取服务端规范化结果并提示 |
| 网络失败 | 持久错误和重试入口 |
| 版本冲突 | 冲突说明、刷新路径和草稿保留路径 |
| 只读或归档 | 说明为何锁定，以及仍可做什么 |
| 媒体失败 | 图片或视频失败占位与 URL 排查提示 |

始终保留可见 `:focus-visible`。状态不能只靠颜色或图标表达。按钮有文本或准确 `aria-label`；图片 alt、视频 label 和外链“新窗口打开”提示随真实内容生成。减少动画规则应覆盖页面以及 portalled Modal、Picker、Message 和 Notification。

## 8. CSS 与组件边界

- 业务类统一使用有语义的 `admin-*` 命名，响应式规则与组件样式放在容易一起维护的位置。
- 少量重复的内联间距改成语义类；不要在多个页面复制同一个 `style={{ ... }}` 片段。
- 全局覆盖 Ant Design selector 只用于无法挂业务类的 portal，并限制在最小范围。普通组件应通过 token、组件 props 或局部类调整。
- 页面负责请求、权限、dirty 状态和白名单 payload；领域组件负责字段、类型能力和预览；纯函数负责规范化和协议裁剪。
- 当 `admin.css` 继续显著增长时，可按 foundation、workspace、editor、domain 拆分，仍由应用单点引入；不要为了拆分切换到另一套 CSS 方案。
- 动效只使用 transform 或 opacity 等低成本属性，并尊重 `prefers-reduced-motion`。不增加持续循环或纯装饰动画。

## 9. 验证清单

UI 改动不能只靠 TypeScript 和构建。至少执行：

```sh
pnpm test:admin
pnpm exec tsc --noEmit
pnpm check:contracts --admin-only
pnpm build
git diff --check
```

然后使用明确指向隔离 API 的浏览器实例，或仅检查不会触发写入的只读页面：

- 视口：`1440×900`、`1024×768`、`768×1024`、`390×844`、`320×568`。
- 浅色与深色，纯键盘、200% 缩放和减少动画。
- 数据量：0、1、15 条；超长中文、长 URL、多图片和失效媒体。
- 状态：loading、empty、invalid、saving、network error、409 conflict、archived/read-only。
- 交互：新增、复制、首尾排序、删除、dirty 关闭、错误 Tab 定位、抽屉焦点恢复。
- 布局：页面无横向滚动，表格只在自身横滚，footer 可见，软件键盘不遮死操作。

浏览器视觉检查必须使用隔离 PocketBase 或纯只读页面。默认线上 API 不能作为自动化或随手写入的 UI 测试库。
