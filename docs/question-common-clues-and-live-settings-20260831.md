# 题目通用线索与已发布场次安全编辑实现说明

状态：2026-08-31 本地实现与隔离验证完成，PocketBase 后端已正式部署并执行增量迁移；玩家端和管理端尚未提交或部署，生产通用线索集合保持为空，未修改线上场次或玩家业务数据。生产过程见 [正式发布记录](question-common-clues-deployment-20260831.md)，后续组件部署与功能激活状态以 [当前生产状态](current-production.md) 为准。

后续状态：同日两个前端已由用户提交并公开部署，静态资产只读检查确认新协议与管理入口存在。本文保留后端发布结束时的原始状态描述；当前集合数量、人工激活和生产写入验收仍以当前状态指针为准。

## 1. 目标与边界

本次把线索拆成两个互补层级：

- **场次线索**继续绑定场次，可按具体玩家下发和保留信件 / 祝福等叙事能力。
- **题目通用线索**只绑定题目。题目被任意场次复用时，完成该题即可看到当前有效的通用线索；配置不要求下线场次。

通用线索支持文字、图片、视频和外部链接，支持是否在首次答对后自动展示。它不支持信件或祝福，也不保存场次、用户、奖励、经验或解锁记录。删除采用归档，避免物理删除造成审计与并发问题。

本次不开放已发布场次的题目替换、关卡增删或重排、经验、惩罚、奖励、参与等级、完成目标、线索触发关系及信件 / 祝福引用。这些字段会改变结算、权限或引用结构，继续通过新版本处理。

## 2. 已发布场次的可编辑白名单

已发布场次使用独立的局部更新接口，绝不调用草稿场次的删除重建保存逻辑。

| 区域 | 发布后可修改 | 继续锁定 |
| --- | --- | --- |
| 基本信息 | 标题、说明 | 系列、版本、状态、参与等级 |
| 场次展示 | BGM 模式与 URL、背景模式与 URL、是否隐藏标题 | 通关演出、完成后目标 |
| 关卡展示 | 已有关卡的 BGM、背景、标题显示覆盖 | 题目、顺序、经验、惩罚、自动下一题、增删关卡 |
| 已有场次线索 | 展示内容、排序、自动展示开关 | 新增 / 删除、类型、触发时机、所属关卡、叙事引用 |
| 奖励 | 无 | 规则、数量、奖品引用 |

接口按字段白名单校验，未知字段直接拒绝；子项 ID 必须属于目标场次。请求携带修改原因、幂等 requestId 和配置版本指纹，事务内再次校验，避免多人编辑相互覆盖。每次成功修改保留安全审计，不记录敏感内容。

## 3. 通用线索数据与配置接口

新增增量集合 `game_question_clues`，核心字段为：

```text
question -> game_questions
position
kind: text | image | video | link
content
autoPlay
status: active | archived
created / updated
```

集合禁止客户端直接读写，只能通过管理员 API 和玩家详情 API 的权限边界访问。管理员读取一组通用线索时获得基于有效记录 ID 与更新时间的版本指纹；批量保存必须回传该指纹。后端在同一事务中新增、更新、重排和归档移除项，版本不一致返回冲突，不做部分保存。

题目列表只返回有效通用线索数量，不把整组正文塞进目录响应。复制题目时复制当时有效的通用线索并生成新 ID；归档题目不可继续编辑线索。

## 4. 玩家可见性与一次性演出

本节描述已经完成并验证的玩家端源码行为；截至本次后端发布结束，线上玩家端尚未发布该版本。由于新集合保持为空，后端先行上线不会向旧玩家端下发题目通用线索。

玩家详情按现有下发归属、场次在线状态和进度做权限检查，然后合并：

1. 已有 `game_clue_unlocks` 中的场次线索；
2. 当前下发中已经完成题目所对应的有效通用线索。

场次线索始终排在通用线索之前。通用线索实例带明确的题目和具体关卡 ID，避免在移动端污染其他题，也不会被误判为多题组合线索。其可见时间由“该题完成时间”和“线索创建时间”稳定计算；读取接口不补写历史解锁记录。

一次性演出不再由前端比较新旧线索 ID 猜测。首次进入场次返回 `transitionEffects`，答题响应返回 `effects`；两者都只描述对应事务真正产生的状态转换，并携带当时的 `autoPlay` 快照：

- 首次进入只返回这次解锁的开始型场次线索；同一请求幂等重放保留原快照，已开始后的新请求显式返回空列表；
- 首次答对时，返回这次真正解锁的场次线索及当时已经存在的该题通用线索；
- 错答、重复提交、普通轮询和详情刷新不产生线索演出；
- 玩家答题后才新增或更新的通用线索会静默进入列表，不补弹窗、不重新自动跳题；
- 玩家随后回答另一题时，也不会误播更早题目后来新增的线索；
- 后台在事务完成后修改线索的自动展示开关，不会反向改变这一次进入或答题演出；
- 幂等重试读取同一命令回执，得到完全相同的 effects 和结算结果。

前端在新后端返回 effect 字段时只按该白名单和快照演出；字段缺失时才回退旧版差量逻辑，以支持滚动发布以及旧命令回执重放。显式空列表表示本次不演出，不能退回猜测逻辑。

## 5. 运营后台交互

本节描述在后端发布结束时尚待用户 push 的管理端源码；该构建随后已公开部署。后续调整遵循 [管理后台 UI 工程与样式规范](admin-ui-engineering-standards.md)。

题目正文与答案仍遵守线上引用锁，但通用线索是独立子资源，可从题目列表或编辑页随时进入。编辑器采用摘要列表和单条渐进展开，而不是一次展开十几张完整表单；支持新增、复制思路式快速填写、上移 / 下移、类型化字段、删除前确认及玩家态预览。

预览明确区分“刚答完此题”和“此前已经答过”：前者展示是否自动弹出，后者固定说明只静默出现在列表。信件 / 祝福不出现在类型选项中。

已发布场次保留完整配置只读查看，并提供单独的“编辑已发布配置”入口，只装载白名单字段。桌面端使用紧凑分组；窄屏抽屉不超过视口、表单改单列、操作区可见，交互保留键盘焦点和减少动画支持。

## 6. 发布与回退边界

本次采用“后端先上线但保持新集合为空”的兼容发布顺序：

1. 完整备份并在隔离副本验证新增迁移；
2. 发布 PocketBase migration、hooks 与 API，同时保持 `game_question_clues` 为空；
3. 发布兼容版玩家端，使其能够识别新 effect 与线索协议；
4. 发布运营后台；
5. 确认玩家端已生效后，才允许配置第一条题目通用线索。

新增集合是可加性迁移，但一旦产生通用线索数据，不允许通过 down 删除集合；回退应保留集合并前向修复，或恢复经验证且确认不会丢失新业务写入的升级前完整快照。管理前端静态发布不会替代后端镜像和数据库迁移。后端发布任务本身未 commit / push、未部署两个前端，也未操作真实玩家、场次或通用线索；两个前端随后由用户自行 push 并公开部署。

本地后端验证只使用项目 PocketBase Docker 镜像和隔离临时数据卷，不要求也不尝试在办公电脑直接启动 PocketBase 原生程序。最终 Docker 全量后端回归为 60/60；玩家端完整检查为 54 个测试文件、232 条测试并完成生产构建；管理端单测、类型检查、契约同步检查和生产构建均通过。
