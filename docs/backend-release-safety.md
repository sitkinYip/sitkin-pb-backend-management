# PocketBase 后端迁移与生产发布安全规范

本文保存 Sitkin 答题服务的长期生产运维方法。具体镜像、哈希、备份路径、维护时间和当次数据差异只写入带日期的 deployment 记录；当前线上指针见 [当前生产状态](current-production.md)。

## 1. 文档职责

| 文档 | 是否随当前状态更新 | 用途 |
| --- | --- | --- |
| `docs/current-production.md` | 是 | 当前镜像、迁移基线、组件部署状态、功能激活闸门和最新记录指针 |
| 本文 | 仅规则变化时 | 长期不变量、失败闭锁、备份和回退方法 |
| 版本专属升级操作单 | 仓库滚动维护，发布包内冻结 | 本次 source、target、迁移、命令、允许差异和回退条件；不可变副本进入发布包 |
| `docs/*deployment-YYYYMMDD.md` | 否 | 当时授权、实际哈希、执行结果和未执行事项的审计快照 |

不得从文件名通配或修改时间猜“最新发布”。生产 Skill 只读取 `current-production.md` 指向的记录。已完成的版本专属操作单不可复用于下一次发布；仓库滚动路径可以在下一次发布前完整替换，但上次冻结副本必须保留在不可变发布包、Git 历史和日期记录中。

已定稿的日期记录不因后续上线而改写当时状态。后来发现原记录存在事实错误时，追加带日期的勘误，保留原叙述、修正内容、依据和修正时间，不静默覆盖审计事实。

## 2. 发布顺序来自兼容矩阵

没有通用的“后端、管理端、玩家端”固定顺序。涉及协议或新数据时，操作单必须回答：

| 组合 | 检查重点 |
| --- | --- |
| 旧玩家端 + 新后端，功能休眠 | 旧流程能否正常解析和运行 |
| 旧玩家端 + 新后端，功能激活 | 是否误播、漏字段、重复执行或错误跳转 |
| 新玩家端 + 旧后端 | 新字段缺失时是否安全回退 |
| 旧管理端 + 新后端 | 原有读取和写入是否继续兼容 |
| 新管理端 + 旧后端 | 是否调用不存在的接口或写入不兼容数据 |
| 新管理端 + 新后端 + 旧玩家端 | 管理端会不会提前产生旧玩家端无法消费的数据 |

发布与激活是两个闸门。后端只有在新能力可以保持休眠且休眠条件可只读验证时才能先行。新管理端如果是新数据生产者，必须晚于对应消费者。每次交接分别报告：源码完成、测试通过、发布包校验、数据库迁移、后端部署、玩家端部署、管理端部署、功能激活、生产业务写入验收。

可选协议字段必须区分缺失、显式空值和非空值。一次性效果要在业务状态转换事务中生成并写入幂等回执；重放返回原快照，不能按当前配置重新推导。权威空结果不能退回客户端差量猜测。

## 3. 授权与预检

代码开发、发布包生成、服务器连接、停服备份、迁移、镜像切换、业务内容写入、真实账号验收和清理是不同授权。执行前逐项匹配用户当前请求。

只读预检至少确认：

- 目标主机、容器、Compose 路径、挂载、回环端口和 CPU 架构。
- 当前实际 image ID、PocketBase 版本、健康与重启计数。
- 当前 Compose 完整哈希和脱敏解析结构。
- 迁移账本、目标集合或字段是否已存在、磁盘空间和备份空间。
- 发布包、源码清单、内嵌 hooks / migrations、目标镜像和版本专属操作单是否一致。
- 当前前端版本、功能休眠条件和回退前提。

preflight 不是锁。真正停服后，在备份、迁移和修改 Compose 前分别重新核对期望旧 image ID、Compose 哈希和迁移基线；任一值变化都停止。镜像 tag 可变，不能代替实际 image ID 或 config digest。

对人工闸门程序支持的普通增量升级，默认使用 [PocketBase 人工闸门发布程序](pocketbase-release-program.md) 生成 pending 盘点计划、冻结 ready 计划和逐阶段状态。不能把脚本当作授权来源，也不能在脚本闭锁后改用临时远程命令绕过同一项检查。程序不支持的迁移类型应先增加新的受审 verifier，或改用新的版本专属流程。

## 4. 发布包和可复现性

- 本机构建、上传完成、服务器解压、Docker 导入后都重新验证 SHA256 和成员清单。
- 冻结 hooks、migrations 和必要运行文件的逐文件摘要，验证镜像内文件与清单一致。
- 发布包不包含 `pb_data`、真实内容、账号凭据、前端构建或可公开日志中的敏感值。
- 若镜像来自未提交工作区，deployment 必须保存完整源码摘要和不可变归档；不能声称 Git commit 可独立复现。
- 版本专属操作单的 source、target、迁移列表必须与 `release.json` 和实际包一致。旧操作单即使命令相似也不能复用。

## 5. 已验证备份的定义

生成归档不等于拥有可用备份。只有完成以下四层验证后，才能标记 `backup-verified`：

1. 停写一致性：停止目标服务，确认没有第二个 PocketBase 打开同一 `pb_data`，完整归档数据目录、实际 Compose、发布信息和匹配代码。
2. 文件级保真：在新隔离目录解压，比较文件类型、符号链接状态、权限、属主、大小和内容摘要。私密目录权限 700，归档权限 600；备份不放在应用、网站或被备份目录内部。
3. 数据库逻辑验证：执行 SQLite integrity 检查，对迁移账本、schema、索引、稳定排序后的逐表记录数和脱敏聚合摘要做基线记录。
4. 目标版本演练：只迁移恢复副本，按允许清单比较前后差异，至少完成一次停止和再次启动，确认迁移不重复且状态持久。

不要只复制运行中的 `data.db`，否则可能遗漏 WAL、附件或设置。AList、CDN、S3 等外部媒体不属于 `pb_data`，需要单独的保留和恢复策略。正式切换完成并写完审计前，不删除唯一经验证的恢复依据。

## 6. 显式迁移与阶段状态机

生产保持 `--automigrate=false`。同一数据目录同时只允许一个 PocketBase 实例打开。推荐的最小阶段为：

```text
prepared
  -> backup-verified
  -> production-migrating -> production-migrated
   | migration-not-required
  -> switching
  -> verified
  -> recorded

任一阶段失败 -> blocked
```

状态文件放在服务器私密发布目录，只写非敏感标识、冻结输入哈希、完成时间和验证摘要。每个阶段只有在前一阶段满足时才能进入；没有迁移的纯 hooks / 镜像发布必须显式走 `migration-not-required`，不能伪造迁移成功。重复执行安全拒绝，或进入只读恢复判断，不能默默重跑；`blocked` 保存故障原因和证据哈希。

每次人工确认最多启动一个服务器 worker。worker 可以在本地隧道断开后完成已经批准的当前阶段，但不得自动进入下一阶段；连接中断时先读取 status，结果未知时禁止盲目重试。第一次危险阶段完成后目标服务会保持停止，后续 migration/no-migration 和 switch 分别需要新的确认，因此维护窗口必须覆盖闸门之间的人工核验时间。

迁移允许差异必须事先列明，包括账本新增项、集合、字段、索引及允许变化的系统记录。迁移账本不仅比较文件名集合，还要对迁移前已有的每条记录计算全字段摘要并要求不变；新迁移在恢复演练与生产执行中的 applied 时间可以不同，但不得借机改写历史记录。迁移后比较全部不在允许清单内的既有业务表、集合定义和脱敏摘要。`sqlite_sequence` 等可选内部对象不得被误写成所有库必然存在；断言要区分“必须存在”“允许不存在”和“必须不变”。

## 7. 失败闭锁

以下任一情况都触发闭锁：命令非零、SSH 或终端中断导致退出状态未知、迁移账本不符、目标 schema 部分出现、迁移前哈希漂移、镜像或内嵌代码不符、恢复副本验证失败。

闭锁后：

1. 不自动重试 `migrate up`，不启动未经确认的新应用。
2. 不运行 migration down，不删半成品表或账本，不自动覆盖数据库。
3. 保留当前完整 `pb_data`、账本、schema、实际镜像、Compose 哈希和脱敏日志。
4. 对“结果未知”先只读判断迁移是否完整完成，而不是假设未执行。
5. 只有服务从未恢复写入、备份已验证、恢复影响已明确且用户批准时，才考虑恢复旧快照；其他情况优先前向修复或只回退应用镜像。

备份阶段失败且生产库、Compose 与迁移账本被证明未变化时，可以恢复原服务；无法证明未变化时继续闭锁。迁移成功但新应用失败时，回退旧镜像并保留加性结构和账本通常更安全。

## 8. PocketBase 0.40.1 空库启动特例

已观察到 PocketBase 0.40.1 在全新空库首次 `serve` 时可能创建内置 installer system superuser。空库测试分为：迁移后首次 serve 前、首次 serve 后、第二次 serve 后。

- 只在无公网、独立临时目录的全新空库中允许版本已确认的固定 installer 系统记录变化。
- 首次 serve 不得新增业务账号、`game_*` 数据或 catalog；第二次 serve 必须全量稳定。
- 恢复副本和生产已有库不允许出现新的 installer 账号，发现即闭锁。
- 不输出该系统记录的凭据。升级 PocketBase 后重新观察，不把 0.40.1 例外泛化到其他版本。

## 9. 切换、验收与回退

2026-11-19 的 `personal-journey-context-v1` 是固定迁移专例：仅新增 context.kind、修改 session.required 并回填历史 kind=session；逐行比较旧三列的类型化摘要，集合只允许指定字段变化及生成的 updated 时间，其他 schema、规则、集合、业务行和历史账本必须不变。不得把这次例外扩为任意 existing-table 迁移。实际 Docker 恢复迁移测试须覆盖有历史行、11 类 SQLite 副本漂移拒绝，以及服务恢复后新 account context 可增长；独立 runner 副本去掉旧行保护的 mutation 必须被负例捕获。

已存在的正式 Push 专用只读挂载只通过固定 `harmony-push-production-v1` profile 保留，不接受任意 additional mounts。固定五项 Push 环境（含 APPROVED=0）、root 私有单硬链接密钥、源 Compose SHA 和旧根清单 Compose SHA 分别锚定；不读取或打包密钥。隔离演练仅挂自己的数据且 network=none，镜像禁止内嵌 Push 环境变量；不能把正式容器配置复制到恢复副本。旧根审计保留历史事实，独立配置变化必须明确登记而非改写旧材料。

切换只修改已确认目标服务的镜像，保持挂载、回环端口、网络、安全选项、健康检查和重启策略。先验证解析后的 Compose 差异，再重建目标服务；不停止 OpenResty、AList 或其他应用，不把 8090 暴露公网。

只读验收至少检查实际 image ID、版本、健康、重启计数、端口、挂载、内嵌代码、迁移账本、schema、允许差异和关键脱敏摘要。健康稳定性必须来自同一容器、零重启以及 Docker health log 中不同的连续成功记录，不能用快速重复读取同一个 `healthy` 值代替。HTTPS 200 与未登录 401 只证明当前公网入口的健康和认证边界；响应未携带冻结 release identity 时，它也不是目标镜像身份或真实业务写入已经验收的证据。

目标服务恢复健康后，真实流量可能在最终记录前更新既有业务行。此阶段继续要求 schema、迁移文件、表列、集合定义不变，并要求尚未激活的新表保持为空；不能再要求全库行摘要与停服快照严格相等，也不能把正常业务写入误当成可自动覆盖的数据漂移。

一旦产生新答题、经验、奖品、领取、核销或新功能数据，旧快照禁止覆盖当前库。先停写保存现状，优先前向修复或只回退应用代码。破坏性 down、删除新增集合和清理迁移账本默认禁止。

## 10. 收尾清单

- 更新 `docs/current-production.md` 的当前镜像、账本、前端状态、功能激活闸门和最新记录指针。
- 更新根 README、`backend/README.md`、`compose.production.yaml` 和功能说明中的当前状态。
- 新增带日期 deployment 记录，写明授权、实际 image ID、完整校验、备份、维护窗口、允许差异、验收、未执行事项和回退边界。
- 把使用过的版本专属操作单标记为已完成；下一次发布必须生成并审查新的操作单。
- 关闭专用 SSH control socket。保留经批准的备份和证据，不顺手删除旧镜像、数据或无关服务。
