# 专属等级头衔与 JSON 扩展配置调研

日期：2026-09-08。本文保留最初源码调研与设计建议。核心功能已在本地实现，准确使用方式、首版限制和发布状态以 [实施说明](extra-config.md) 为准；生产尚未迁移或发布。

本文基于两个本地仓库的迁移、hooks、接口协议和玩家端解析代码，不代表对生产数据库实际 schema 或业务数据的盘点。当前迁移源码定义 24 个 `game_*` 集合：初始化 22 个，随后新增题目通用线索和题目设置两个集合。

## 1. 结论与本次建议

可以实现：首次建设扩展配置能力后，运营在后台定义和下发新的展示字段，后端统一校验、存储并按范围返回，前端接入字段时无需再次增加数据库列。已有通用组件支持的配置可以纯后台调整；全新交互仍需要前端代码，涉及业务规则的变化仍需要后端代码，涉及关系、索引、唯一约束的变化仍可能需要迁移。

推荐新增三个私有集合：

1. `game_player_level_titles`：专属头衔业务记录，保留用户、等级、名称等明确字段，并预留 JSON `extra`。
2. `game_extra_definitions`：后台可维护的扩展字段定义，限定数据类型、使用范围、客户端用途和校验约束。
3. `game_extra_configs`：关联目标与接收用户，使用 JSON `extra` 保存实际配置。

现有业务表先不批量加 `extra` 列，由统一配置表关联这些对象；API 在对应对象上返回解析后的 `extra`。这仍然满足“用户、场次、关卡有扩展字段”的使用体验，避免分散实现和重复存储。以后新建确有独立附加数据的业务表，可以按同一规范预留 `extra`，但必须明确唯一数据源。

本方案是一套有明确范围的配置能力，不提供任意脚本、任意数据库字段写入或任意业务规则编排。

## 2. 当前表与 JSON 字段盘点

下表覆盖迁移源码中的全部 24 个集合。“统一关联”表示可作为扩展目标，不表示本次立即开放所有对象类型。

仅增加 JSON 列不会打通功能，现有代码有三层边界：

- `backend/pb_hooks/lib/db.js` 的 `pick()` 只返回声明字段；`gameplay.js`、`admin.js` 在多个接口显式构造 DTO。
- `backend/pb_hooks/lib/clues.js` 等对 JSON 内容实行字段白名单；已有 `presentation`、`content` 不能直接当作任意扩展容器。
- 玩家端 `src/api/game.schema.ts` 使用显式 `z.object()`。本地使用项目已安装 Zod 验证：未声明的 `extra` 会被解析过滤，必须首次改造协议和解析器。

## 3. 新集合设计建议

### 3.1 专属等级头衔

`game_player_level_titles` 建议字段：`player` relation、`level` relation、`name` text（最多 60 字符，与默认名称一致）、`status`（active/revoked）、`extra` JSON、`revision`、创建／更新时间。建立 `(player, level)` 唯一索引；下发、修改和撤销记录操作者、原因及 before/after 审计。

- 现有 `game_level_definitions.name` 始终是默认名称，不覆写。
- 专属名称按当前真实等级 ID 匹配；未配置或撤销时回退默认名称。
- 允许预配置未来等级，升级后生效；升级到其他等级不沿用上一等级头衔。
- 玩家响应 `level.name` 和 `nextLevel.name` 返回最终展示名称，可补充 `defaultName`、`customTitle` 可选信息；管理端全局 ranks 继续返回默认定义。
- 第一版下一等级预告也显示已配置专属名称；如果改成升级时揭晓，需统一调整预告规则。
- 下发本身只更新资料，不自动播放“等级突破”。专门的获赠弹窗需要独立事件、快照、消费记录和重试约定。
- 本表 `extra` 仅预留头衔附加展示信息。首次无已接入字段时按空对象处理；以后注册专用命名空间并校验，不能借此覆写 `name`、`player` 或 `level`。
- 通用配置不能再定义另一份“专属头衔名称”。头衔名称由本表唯一负责，等级通用装饰与头衔附加信息必须使用不同命名空间。

### 3.2 字段定义

`game_extra_definitions` 每行定义一个命名空间，例如 `profileGreeting`、`questHeader`。建议固定列：`key`（唯一、启用后不可改名）、`label`、`status`、`schema` JSON、`revision`、创建／更新时间。

`schema` 使用服务端预先实现的有限声明格式，不执行代码。至少描述：

- 对象属性名、类型（短文本／多行文本／数值／布尔／枚举／URL／受限数组和对象）、必填项和默认值。
- 长度、数值范围、枚举值、数组长度、对象层数。
- `allowedScopes`、`outputContexts`、`visibility`（player 或 admin）、是否允许在线编辑。
- 客户端组件标识及兼容版本（如果希望通用组件直接展示）。组件标识只能来自已实现的组件清单。

普通展示字段可以由后台创建，无需每增加一个键修改 hooks。注册了字段不代表前端已经实现它；后台必须显示“仅传输／已有组件支持”的区别。业务保护策略、可用对象类型、服务器规则和渲染器代码不由该声明自由扩展。

已激活定义的类型、含义、可见性和范围不能直接破坏性变更；建议使用新命名空间，例如 `questHeaderV2`。兼容地增加可选属性可以更新定义，但须校验存量配置、维护 revision 并保留审计。内部字段改为玩家可见应新建公开定义并重新下发，不能把历史内部数据直接暴露。

### 3.3 配置记录

`game_extra_configs` 每行保存“一个命名空间 × 一个目标 × 一个接收对象”的配置。建议字段：

| 字段                             | 用途                                               |
| -------------------------------- | -------------------------------------------------- |
| `definition` relation            | 关联字段定义                                       |
| `scopeType` text                 | 固定服务端注册表中的目标类型；不能接受任意集合名称 |
| `scopeId` text                   | 目标记录 ID；global 使用固定空值                   |
| `assignment` relation，可选      | assignment_level 的任务关联，其他类型留空          |
| `player` relation，可选          | 指定接收用户；公共配置留空                         |
| `targetKey`、`recipientKey` text | 服务端生成的规范化索引键，不接受客户端自定义       |
| `extra` JSON                     | 当前命名空间的完整对象值，不存放用户 ID 列表       |
| `mode`                           | value 或 suppress；后者显式屏蔽该命名空间          |
| `status`                         | active 或 revoked                                  |
| `revision`                       | 乐观并发版本                                       |
| `lastRequestId`、创建／更新时间  | 关联操作批次和记录版本                             |

唯一索引：`(definition, targetKey, recipientKey)`；读取索引围绕 `targetKey`、`recipientKey`、`status`，具体组合在隔离库查询计划与数据量测试后确定。

`scopeType + scopeId` 是多态引用，数据库不能自动验证目标表和所属关系，因此服务端必须检查目标存在、类型合法、版本／状态和任务归属，复制／删除对象时必须处理绑定。若后来需要跨目标高频 join 或强数据库外键保证，应提升为专用 relation／集合，而不是继续扩大 JSON。

所有新集合直接 list/view/create/update/delete 规则保持私有，玩家仅经受控业务 API 获得自己的有效配置。管理员内部配置不得通过认证响应、玩家集合直读或自助资料更新接口泄漏。

## 4. 下发范围：对象与用户分开选择

第一版支持以下对象。这里“等级”是成长等级，“关卡”是场次中的小关卡，两者不能用同一个 level 字段混称。

| 目标             | 含义                                         |
| ---------------- | -------------------------------------------- |
| global           | 用户资料等全局上下文                         |
| rank             | 某个成长等级 ID                              |
| question         | 某个题目版本 ID，影响其被使用的合规上下文    |
| session          | 某个场次版本 ID                              |
| session_level    | 某个场次中的某个小关卡 ID                    |
| assignment       | 某用户的一次场次任务 ID                      |
| assignment_level | 某次任务＋该场次某个小关卡，精确覆盖一次参与 |

用户范围有三种，后台必须分开命名：

1. 指定用户：将去重后的有效用户逐个写入配置；禁用用户列为跳过，并在预览和结果中显示。
2. 全部当前有效用户：与现有任务下发一致，保存执行时的用户快照，之后新建账号不自动获得。重复请求返回首次接收者和结果，不重新扩大名单。
3. 公共默认配置：不展开用户，在读取时对有权访问目标的用户生效，包含未来新用户。这不是“全部当前用户下发”。

assignment／assignment_level 本身只属于一个用户，禁止给无关用户或公共人群绑定。场次／关卡配置也不授予入场、解锁或阅读权限。

首版采用有上限的单事务批量下发。建议同时限制用户数量、配置行数、请求字节和审计大小；超过限制明确拒绝，不偷偷分批造成部分成功。后续需要超大批次时，再独立设计持久化批次、进度、失败重试和分批撤销。

预览展示目标、当前用户数量、现有覆盖、将创建／更新／跳过项及版本指纹；执行时重新核验指纹，用户集合或配置变化则要求刷新预览。批量撤销只撤销该批次仍未被后续修改的记录，发现 revision 变化应报冲突，不能覆盖后来管理员的修改。

## 5. 生效优先级与缺省语义

采用固定、可解释的优先级，不开放运营手填任意 priority：

- 玩家资料上下文：global → rank；每个 scope 内公共默认先于指定用户。
- 答题小关卡上下文：global → question → session → assignment → session_level → assignment_level；每个 scope 内公共默认先于指定用户。
- 场次概要仅使用 global → session → assignment，不合并关卡或题目配置。
- 定义通过 outputContexts 决定进入哪些输出位置；资料字段不能因为 global 目标而流入所有题目。

后者覆盖前者，即对象具体程度优先于用户具体程度。例如个人 global 值会被某个具体关卡的公共配置覆盖；要只改这个人的关卡，应给他下发 session_level 或 assignment_level 配置。后台预览必须展示最终值及来源，避免用户靠猜测理解覆盖。

以整个命名空间为替换单元，不对未知嵌套对象做深合并，数组整体替换。字段定义的默认值只在最终胜出的对象内部补齐；没有任何有效配置时不凭定义自动激活功能。

- 缺少绑定／撤销：不贡献值，继续继承较低优先级配置。
- mode=suppress：该层显式屏蔽命名空间，较高优先级仍可重新赋值。
- extra={}：显式空对象，经字段定义校验后替换继承对象，可能补齐声明默认值；不等于撤销。
- null：首版不支持，拒绝写入；空字符串和 false 在字段允许时是有效值。
- 更新请求必须明确 value／suppress／revoke，不能将缺失 extra 猜成清空。

首版不做时间窗口和多条定时配置；以后需要到期机制，需补充过期、缓存、重放与冲突规则，不能只随意在 JSON 中放一个 expiresAt 就期待自动执行。

## 6. 接口、前端与内容边界

新增建议模块 `backend/pb_hooks/lib/extra-config.js`，统一完成字段定义校验、目标／用户检查、解析、优先级、批量预取、并发与审计。管理接口建议提供定义 CRUD（含软停用）、配置查询、下发预览、提交／撤销和效果预览，路径可集中在 `/admin/extra-definitions` 与 `/admin/extra-configs`；这都是待实现接口。

复用 `db.command()` 的事务与幂等、`db.audit()` 的审计格式和既有版本指纹模式。下发／撤销必须填写原因和 requestId。首次改造后，新增受支持数据类型的普通展示字段无需新增 API 路由。

玩家接口在既有对象上添加可选 `extra`，例如：

```json
{
  "extra": {
    "profileGreeting": { "text": "欢迎回来，星河守护者" }
  }
}
```

字段含义由命名空间定义和前端适配器约定；不得将 extra 展开到 DTO 顶层覆盖既有字段。共享协议声明受限 JSON 类型／字典，玩家 Zod 只在 extra 容器内保留自定义键，核心对象继续显式校验；组件对已识别命名空间再次做类型校验，未知命名空间忽略，损坏的可选配置隔离降级，不能让整个答题页面失败。

第一版只支持普通展示和被动 UI 参数，不从 extra 读取经验、答案、判题模式、参与资格、奖励数量、奖励状态、解锁条件、任务进度、认证角色、一次性演出或内容访问引用。仅过滤 xp 等键名不够，核心业务代码必须根本不消费通用 extra 作为权限或结算输入。

具体访问边界：

- 当前 `gameplay.detail()` 会将未解锁／未来题目设为 question=null。新增 extra 不得绕过该限制；相应题目和关卡扩展在合法可见时才返回。
- 当前线索只返回已解锁内容，叙事有单独访问校验。以后扩展这些对象也沿用同样规则，不开放“输入任意目标 ID 读取配置”的玩家接口。
- 在线配置编辑首版仅允许无业务副作用的展示字段；不能借通用 JSON 绕过已发布场次的结构锁和题目引用锁。
- URL 沿用服务端和玩家端的安全 URL 处理；不允许运营字段嵌入脚本、任意 HTML、代码表达式或执行型组件配置。
- 命名空间和对象键禁止 `__proto__`、`prototype`、`constructor` 等危险键。配置对象建议初始上限 16 KiB、深度 4、每层 50 键、数组 50 项，聚合响应也要有总上限；最终值需结合实际 UI 内容确认。

读取按用户和当前合法上下文批量查配置并使用请求内缓存，避免在 catalog 的每个玩家／题目循环中新增逐行查询。不能默认把所有用户的所有配置塞进 catalog；配置管理应独立分页查询。第一版不增加跨请求缓存，已有玩家资料 5 秒轮询可复用；关卡配置需核对详情查询与刷新行为，不承诺所有页面都在同一时间更新。

## 7. 版本、复制、历史与快照

- 配置绑定具体记录 ID，不绑定可变名称、等级序号或关卡位置。场次新版本不会自动继承旧 ID 的配置。
- 复制题目／场次时，旧绑定默认不复制；需要复制公共展示配置时提供明确选项，并重映射小关卡 ID。个人与任务专属配置不自动复制。
- 被引用对象归档／下线后，读取继续服从原有访问策略。硬删除需清理或拒绝残留绑定，不能依赖多态字符串自动级联。
- 普通展示配置按当前值解析，修改后可影响旧任务重新打开时的展示；后台需说明这是实时展示，不是历史归档。
- 奖品名称／领取说明、解锁效果、一次性演出等历史内容仍使用发放／触发时快照。若将来需要支持这些扩展，在业务事务中保存批准字段和配置版本，进入幂等结果，不能在重试时重新解析新配置。
- 不在读取接口创建“已领取”或“已展示”记录。获赠弹窗、奖励和统计埋点消费是独立能力。

| 需求例子                                             | 数据库迁移               | 后端代码               | 前端代码                           |
| ---------------------------------------------------- | ------------------------ | ---------------------- | ---------------------------------- |
| 修改已有专属头衔名称、给另一个用户下发               | 不需要                   | 不需要                 | 不需要                             |
| 修改已有组件支持的欢迎语／角标                       | 不需要                   | 不需要                 | 不需要                             |
| 新增受支持类型的字段，作为新页面展示文本             | 不需要                   | 通用机制覆盖时不需要   | 需要消费该字段；已有通用插槽可例外 |
| 对特定用户／全部当前用户／特定场次／关卡下发上述配置 | 不需要                   | 已支持范围内不需要     | 组件已经接入时不需要               |
| 新增动态页面／复杂交互／定时生效                     | 通用存储可能够用         | 根据语义需要           | 通常需要                           |
| 新增领取、发奖、经验、权限或解锁规则                 | 根据约束决定             | 需要                   | 根据功能决定                       |
| 新增不在对象注册表内的下发目标类型                   | 通用表可能够用           | 需要目标适配和权限检查 | 后台与玩家端按用途接入             |
| 自定义字段需要高频筛选、排序、统计、唯一约束、强关联 | 通常需要专用列／索引／表 | 需要                   | 按用途接入                         |

判断标准是字段承担的职责，而不是“看起来只是多一个字段”。达到业务事实、关系或查询约束级别时，应从 JSON 提升为结构化模型。

## 9. 迁移与兼容策略

当前 `additive-empty-collections-v1` 发布 verifier 只支持无迁移，或新增且发布时为空、规则私有的集合。给既有多张表加 extra 列不在该支持范围内，若选该方案必须另外实现并审查 verifier／专属操作单，不能直接套用现有程序。

因此推荐本次只新增上文三个私有空集合，不改旧表，不回填，不在迁移中写入字段定义或头衔。结构发布、应用上线、创建字段定义和实际下发分别记录。这个方向符合现有 verifier 的支持类别，最终是否通过仍以真实生成的 schema 差异、空库测试和恢复副本验证为准。

| 组合                       | 必须保证                                                                 |
| -------------------------- | ------------------------------------------------------------------------ |
| 旧玩家端＋新后端（无配置） | 原响应保持兼容，默认头衔不变                                             |
| 旧玩家端＋新后端（有配置） | extra 被忽略，不依赖旧端执行新功能；解析后的 level.name 仍可展示专属头衔 |
| 新玩家端＋旧后端           | extra 缺失回退空对象，头衔额外信息可选                                   |
| 旧管理端＋新后端           | 全局等级保存不删除专属记录，旧内容保存不擦除独立 extra 绑定              |
| 新管理端＋旧后端           | 先检查后端能力，禁用不支持的入口，不能静默保存失败                       |
| 新管理端＋新后端＋旧玩家端 | 默认保持未激活；只有明确支持旧端忽略的被动展示字段才可提前下发           |

后端可以在三张表为空时先上线；字段定义和配置的实际激活需在受影响客户端可兼容之后。回退旧 hooks 只隐藏新能力并保留新表，不能执行破坏性 down migration。不要因回退应用而恢复旧库覆盖发布后产生的答题数据。

## 10. 实施清单与验收

建议分成两个可独立验收的工作包，同轮规划：

1. 专属头衔：新表含 extra、管理员配置抽屉、查询／保存／撤销接口、当前／下一等级统一解析、升级弹窗回归。
2. 通用扩展：定义和配置两张表、通用校验及下发接口、范围解析、后台字段管理与效果预览、两端协议透传，至少用“用户欢迎语”和“指定用户指定关卡提示文案”完成真实组件接入闭环。

要实现本次提出的“后台自定义下发、前端直接接入”目标，第二包不能只预留空 JSON 字段，必须完成配置编辑、保存、读取与消费者验证；具体页面样式、批次上限和首批组件在实现阶段沿用现有 UI 规范确认。

涉及文件：新增迁移；`backend/pb_hooks/lib/extra-config.js`、`api.js`、`gameplay.js`、`admin.js`；`backend/contracts/game.ts` 及两端同步副本；后台 OperationPages、独立配置编辑组件和审计标签；玩家 `src/api/game.schema.ts`、资料／侧栏／等级演出及首批扩展展示组件。

最低验收包括：

- 空库／旧库恢复副本迁移、两次重启稳定；旧表和旧业务记录无额外变化；三个新集合保持私有。
- 头衔默认回退、用户隔离、升级／降级匹配、下一等级、撤销、重复请求与并发冲突。
- 全部当前用户快照与公共默认的区别、未来用户、禁用用户、目标版本、任务所属关系。
- 优先级、整对象替换、缺失／空对象／false／suppress／revoke、并发下发与批量撤销冲突。
- 定义变更兼容、未知命名空间、旧客户端过滤、坏字段隔离、大小／深度限制、危险键和 URL 校验。
- 私有字段、未入场／未来题目／未解锁线索不泄漏；伪造用户 ID 或目标 ID 被拒绝。
- 奖励、经验、入场资格、已发布结构锁和一次性 effect 重试语义不受 extra 影响。
- 使用足够数量的用户和关卡测查询次数、响应体、批量事务和审计容量；不得仅验证单用户样例。
- 同步并检查共享协议，运行受影响后端隔离测试、管理端检查和玩家端检查，再做界面验收。

最初调研仅新增本文及文档入口。随后用户确认实施，已完成本地改造；测试和发布状态另见 [本次实现与验收](extra-config-validation-20260908.md)，不将设计建议直接当作生产生效状态。
