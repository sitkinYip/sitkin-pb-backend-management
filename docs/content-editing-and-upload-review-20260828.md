# 发布内容编辑、富文本说明与上传文件名评估

日期：2026-08-28。结论基于后台仓库和 `questions-web` 当前代码；没有查询或修改线上业务数据。

当前范围：第 1 项仅调查和估算；用户后续确认执行第 2 项，富文本说明恢复已完成。第 2、3 项均已实现并本地验证，未发布。

## 1. 发布冻结来自哪里

- 后台 `src/game/ContentPages.tsx` 的题目、场次、叙事编辑器均以 `status !== "draft"` 判断只读，隐藏保存入口。
- 后端 `backend/pb_hooks/lib/admin.js` 的 `version()` 在非草稿、非克隆操作时返回 HTTP 409 / `PUBLISHED_IMMUTABLE`。三个保存入口共用这条规则。
- 这是上次重构的业务设计，不是 PocketBase 天生不允许修改。`backend/README.md` 明确说明发布内容冻结；业务集合的直接写接口也已关闭。

### 为什么不能只删判断

1. **场次保存目前是草稿式全量重建。** `saveSession()` 会删除旧 `game_reward_rules`、`game_clues`、`game_session_levels`，再生成新 ID。进度、提交记录、经验流水、已解锁线索和奖品记录引用这些旧 ID。数据库关联约束可能阻止删除；即便绕过约束，也会破坏历史关联，不能把它当作线上内容编辑接口。
2. **玩家没有完整题目/场次快照。** 下发记录绑定场次版本 ID；入场保存的是准入信息，非完整内容。`gameplay.detail()` 每次读取关联场次、关卡、题目和线索，`answer()` 每次读取当前答案表。已发奖品另有快照，但这不能保护整场答题。
3. **同一题目版本可能被多个场次复用。** 修改题目会影响所有引用者，包括历史回顾。不能只检查眼前这个场次有没有玩家。
4. **前台会很快读到更新。** `questions-web/src/features/game/GamePlayPage.tsx` 每 5 秒刷新详情；输入答案按关卡 ID 保存、当前页面按关卡下标导航。改 ID、增删或排序会使进度、输入和当前展示不再对齐。改答案也可能造成玩家看到旧题面却按新答案判分。
5. **改经验、惩罚和奖励不是自动重算历史。** 已完成关卡不会因改配置自动补发经验；历史奖品也不会自动变更。错误次数、冷却及锁定状态需要明确迁移或补偿规则。

### 建议的编辑策略与成本

以下为当前代码下单人实现、含本地回归的工程量粗估，不含上线协调或大规模历史数据修复。

| 范围 | 建议 | 粗估 |
| --- | --- | --- |
| 已发布、没有任何当前或历史下发引用的内容 | 可以开放完整编辑；必须检查题目/叙事的全部引用关系，保存后重新做发布完整性校验 | 0.5–1 天 |
| 已经使用的内容：标题、题面文字、提示、图片、BGM、背景、现有线索正文等展示字段 | 增加字段白名单和独立补丁接口，原地保留关联 ID；记录修改前后和理由、提示影响范围，并处理并发编辑 | 1–2 天 |
| 已经使用的内容：答案、选项标识、题型、关卡增删排序、经验、奖励、触发规则 | 默认保留新版本流程；若要原地改，需要设计已有玩家进度迁移、旧题面提交保护、历史解释及补偿规则 | 3–7 天起，依迁移策略再细化 |

展示字段可编辑也不是零风险：修改题面含义或线索仍会改变体验，历史回顾也会展示修改后内容。推荐默认提供“修正文案/媒体”，而非“全部解锁”。如果要求老玩家始终看到旧内容，则要继续使用版本或引入内容快照。

当前“新版本”不会自动迁移旧下发：场次克隆仍引用原题目版本；题目有新版本后，还需在新场次中选择它。`assign()` 会跳过同系列仍在 assigned/active 的玩家，已完成人员默认也跳过，除非明确重发。因此现有流程确实不适合频繁小修。

### 第 1 项需要修改的项目与发布边界

- **管理端网页必须改**：本仓库 `src/game/ContentPages.tsx` 的编辑入口、字段只读规则、保存请求和影响提示；若扩展请求结构，还需同步契约。
- **PocketBase 后端服务必须改**：本仓库 `backend/pb_hooks/lib/admin.js` 的冻结判定、字段白名单、保留关联 ID 的更新路径，以及引用检查、审计、并发保护和对应后端回归。不能只解除前端 disabled，也不能直接复用现有场次全量重建路径。
- **答题页视范围而定**：仅调整现有展示字段、保持返回结构及关联 ID 不变，`questions-web` 预计无需功能修改，但应联调回归；若改答案或关卡结构，需要配套旧题面提交保护、导航及输入状态处理。
- 安全展示字段补丁方案预计不需要数据库迁移；若引入内容快照或新的并发版本字段，则需另行设计。管理端与后端服务虽然在同一仓库，部署仍是两件事，单独发布管理端静态资源不会更新 PocketBase。

## 2. 富文本提示为何消失

原组件 `TextSyntaxHelp` 定义在 `src/pages/levels/components/ThreadEditor.tsx`，旧线索及通知表单引用它。新版路由改用 `src/game/ContentPages.tsx` 和 `src/game/OperationPages.tsx` 后，没有接入这个说明组件，是迁移遗漏。

答题页仍有 `RichContent` / `parseLegacyContent`，支持高亮、链接、图片、视频及真实换行。恢复说明不涉及数据库迁移，也不需要改接口。

已提取为独立共享组件 `src/components/TextSyntaxHelp.tsx`，在题面正文、可展开提示、线索文字、通知正文、奖品公共领取说明、专属领取信息共 6 类字段旁接入。线索的文字内容在移动端卡片预览和桌面手记中也使用富文本渲染，所以不只文字类型线索显示说明。保留的旧表单统一改用共享组件，移除重复定义。

当前选项文字、信件打字机正文、祝福粒子文字并不是通用富文本渲染，没有添加误导性说明。

旧说明需要同步校准，不能原样照搬：

- 当前解析器识别真实回车换行，不把字面量 `\n` 两个字符当成换行。
- 外链仅接受 HTTP(S)，站内链接必须以单个 `/` 开头；并非任意非 HTTP 字符串都能跳转，旧路由也不保证仍可用。
- 富文本内嵌图片目前直接显示，没有绑定点击大图预览；题面独立图片字段另有预览能力。

原估算为 1–3 小时；本次已按用户确认恢复准确说明，包含示例和资源上传后的 CDN 链接使用提示，不包含实时预览或语法插入按钮。说明放在 `Form.Item.extra` 中，默认折叠，不改变输入绑定、保存数据和发布只读限制。

验证：新增 5 项说明组件及表单接入回归，连同此前测试共 21 项通过；构建与契约检查通过。Browser 使用临时隔离数据验收真实管理表单，验证 6 类字段说明、动态新增线索、键盘收起、输入保留、只读表单可查看说明，以及浅色/深色布局。未连接线上后端，未执行保存或发送通知。临时预览服务与夹具已清理。

## 3. Alist 上传前重命名：已实现

原 `uploadFile()` 同时用 `file.name` 构造存储路径和 CDN URL，资源管理的大文件轮询也按原名查目录。

新行为：

- 所有通过本后台上传的图片、视频、音频，都先生成 128 位密码学随机值的 32 位小写十六进制文件名。
- 例如 `关卡背景 图 #1.PNG` → `9f645831a0274ad19fb76dc3ba2e6801.png`（仅格式示例）。
- 保留并小写化有效扩展名；没有有效扩展名时按常见媒体 MIME 推断，无法识别则用 `.bin`。不转码，不修改本地原文件和字节。
- 上传的 `File-Path`、返回 CDN URL、大文件轮询使用同一新文件名。表单自动填入新 URL，资源管理列表展示实际存储名。
- 使用 `crypto.getRandomValues`，兼容项目 HTTP 开发域名，不依赖仅安全上下文可用的 `randomUUID`。
- 不改已有文件和数据库中的旧链接；不新增依赖，不需要改 PocketBase 或 Alist 服务端。

实现依据：[AList 流式上传 API](https://alistgo.com/zh/guide/api/fs.html) 用 URL 编码后的 `File-Path` 指定完整目标文件路径，二进制请求体不必改动。

随机命名还降低同名覆盖与复用旧 CDN 缓存键的风险。代价是资源列表无法再按新上传文件的中文原名搜索；目前不持久化原名映射。同一个文件重复上传会得到多个独立对象，不提供内容去重。历史文件名和历史链接编码问题不在本次修改范围。
